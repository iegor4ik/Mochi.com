# 🎮 GAME INTEGRATION — онлайн-игра как третья часть M-o-chi.com

> Техническая инструкция по добавлению **онлайн-2D-игры** (открытый мир, кастомные карты,
> внутриигровой чат, игровые «сервера») в проект mochi-forum как **третьей части сайта**.
> Файл самодостаточный: рассчитан и на ИИ-агента, и на живого разработчика.
> Дополняет `PROJECT_CARD.md`, ничего в нём не отменяет. Обновление: 2026-09-16.
>
> Как читать: §1–§3 — принципы, стек, маршрутизация; §4–§9 — что и где создавать;
> §10 — порядок работ по шагам; §14 — отдельное решение по Mochi chats.

---

## 1. Главный принцип (прочитать до написания любого кода)

Игра — **часть сайта для пользователя**, но **отдельный сервис технически**.

| Оставляем общим | Делаем отдельным |
|---|---|
| Домен m-o-chi.com, визуальный стиль, тема | Процесс Node.js: `game-server/`, порт **3001** |
| Аккаунты и JWT (тот же `JWT_SECRET`) | База данных: отдельный Postgres `game-db`, порт **5434** |
| Общие скрипты `api.js` / `ui.js` / `theme.js` | Каталог кода: внутри `server/` игры не будет вообще |
| Единая точка входа nginx | Жизненный цикл: деплой/рестарт/падение игры не трогает форум |
| Русский язык интерфейса и комментариев | Зависимости: свой `game-server/package.json` |

**Правило изоляции.** Падение, утечка памяти или рестарт игрового сервера не должны влиять
на форум и чатсы — и наоборот. Для ИИ-агента это жёсткое ограничение: **никаких** игровых
роутов, таблиц и зависимостей в `server/` и основной БД, даже «временно». Для человека:
если появился соблазн «пусть полежит в общем сервере» — не поддаваться.

Почему это не перестраховка: в Node.js падение процесса = смерть всего процесса. Игровой
цикл, таймеры синхронизации и WS-хендлеры — типичные источники необработанных исключений
и утечек. Изоляция процессов — самая дешёвая страховка из существующих.

При этом игра **не обязана** деградировать вместе с форумом: если основной API временно
недоступен, уже установленные игровые сессии продолжают работать (см. §5).

## 2. Стек

| Слой | Выбор | Почему / примечание |
|---|---|---|
| Рендер 2D | **Phaser 3**, одним `<script>` (файл в `public/js/game/vendor/` или CDN) | tilemap-поддержка, камера, спрайты; вписывается в «без сборки» |
| Кастомные карты | **Tiled** (mapeditor.org) → JSON → `JSONB` в БД игры | стандарт де-факто; JSON валидируется на сервере до записи |
| Realtime | **ws** (минимализм) или **socket.io** (комнаты/реконнект из коробки) | поллинг как на форуме для игры непригоден (latency и трафик) |
| REST игры | **Node.js ≥ 18 (CommonJS) + Express 4** | те же конвенции, что в основном сервере |
| БД | **PostgreSQL 16**, отдельный инстанс `game-db` | изоляция данных и сбоев |
| Reverse proxy | **nginx** на Ubuntu-хосте | `/` → 3000, `/game/*` → 3001, отдельный location для WS |
| Запуск | **docker-compose** (как сейчас) + `restart: unless-stopped` | альтернатива без Docker: systemd-юниты + PM2 |

Чего избегать: сборщики/бандлеры и npm на фронте, второй язык бэкенда (Go/Elixir) без
крайней необходимости, объединение процессов «всё в одном», общая БД, TypeScript и
фронтенд-фреймворки — стек проекта единый: vanilla JS + CommonJS + Express + Postgres.

## 3. Порты, домен и nginx

| Компонент | Внутри Docker | На хосте (dev) |
|---|---|---|
| Основной сайт (форум + чатсы) | 3000 | 3000 |
| БД основного сайта | 5432 | **5433** |
| Игра: REST + WebSocket | 3001 | 3001 |
| БД игры | 5432 | **5434** |

Единая точка входа — nginx (80/443). Игра живёт **на том же домене, в пути `/game/`**,
а не на поддомене: тогда у страницы игры тот же origin, и `localStorage.mochi_token`
читается напрямую, без проброса токена через query/cookie.

```nginx
# основной сайт (форум, чатсы, статика, /api)
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

# игра: REST (префикс /game срезается → внутри game-server пути /api/*)
location /game/ {
    proxy_pass http://127.0.0.1:3001/;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}

# игра: WebSocket (отдельный location обязателен!)
location /game/ws {
    proxy_pass http://127.0.0.1:3001;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

Соглашение об адресах: в браузере — `https://домен/game/api/health` и
`wss://домен/game/ws`; внутри game-server — `/api/health` и `/ws`. Оболочка игры
`game.html` отдаётся основным сервером как статика (так же, как `chats.html`), см. §8.

Грабля nginx: без `proxy_http_version 1.1` + `Upgrade` WS-соединения рвутся сразу или
через ~60 с (дефолтный `proxy_read_timeout`).

```
│   ├── chats.html           ← чатсы (не трогаем)
│   ├── game.html            ← НОВОЕ: оболочка игры, третье SPA

│   └── js/game/             ← НОВОЕ: код игры (роутер, ws-клиент, сцены Phaser)
│       └── vendor/phaser.min.js
├── server/                  ← основной сайт. НЕ расширять игровым кодом!
├── game-server/             ← НОВОЕ: отдельный сервис игры
│   ├── package.json         ← свои зависимости (express, pg, ws, dotenv)
│   ├── .env.example
│   ├── Dockerfile.game
│   ├── db/migrations/       ← СВОИ SQL-миграции 001… (журнал schema_migrations)
│   ├── scripts/             ← migrate.js (копия паттерна из server/scripts), тесты
│   └── src/
│       ├── index.js         ← express (REST) + ws-сервер на одном порту 3001
│       ├── config/db.js     ← pg.Pool к game-db (копия паттерна config/db.js)
│       ├── middleware/auth.js   ← проверка JWT тем же секретом
│       ├── routes/          ← REST: миры, карты, участие, статистика
│       └── realtime/        ← ws: комнаты-«сервера», синхронизация, игровой чат

```

Правило принадлежности кода: файл либо весь игровой (→ `game-server/`, `public/js/game/`),
либо весь форумный (`server/`, `public/js/…`). Общие фронтовые скрипты (`api.js`, `ui.js`,
`theme.js`) остаются в `public/js/` и подключаются из `game.html` по относительному пути —
это тот же паттерн, что у `chats.html`.

## 5. Аутентификация и связь с основной системой

Юзеры создаются **только на форуме**. Регистрации/логина в игре нет.

1. **Один `JWT_SECRET`** в env обоих сервисов. Игровой сервер сам проверяет подпись и
   срок токена (порт `server/src/middleware/auth.js`, адаптированный под game-server).
2. Токен при WS-подключении передаётся **первым кадром после открытия соединения**
   (`{type:'auth', token}`), а не в query-параметре — чтобы токен не попадал в
   access-логи nginx. До успешного auth-кадра сокет не допускается в комнаты и
   закрывается по таймауту (~10 с).
3. **Данные юзера** (ник, аватар, роль): игровая БД хранит только `user_id INTEGER`
   без FK — базы разные! Профильные данные получаются запросом к основному API через
   внутренний эндпоинт (`GET /api/internal/user/:id` — отдаёт минимум: id, username,
   avatar, role, is_banned; без email) и **кэшируются в памяти на 5–15 минут**.
4. **Баны**: проверять при подключении и периодически (раз в ~5 минут) для активных
   сессий. Бан из админки форума автоматически действует и в игре.
5. Если основной API недоступен: активные сессии живут на кэше, новые подключения
   отклоняются с понятной ошибкой. Это осознанная деградация, а не сбой.

`MAIN_API_URL` (например, `http://app:3000` внутри compose-сети) — единственная точка
соприкосновения двух сервисов. Прямых обращений game → основная БД и app → game-db
не существует.

## 6. База данных игры

- Миграции: `game-server/db/migrations/001_init.sql`, … — паттерн тот же: идемпотентность
  (`IF NOT EXISTS`), журнал `schema_migrations`, скрипт мигратора копируется из
  `server/scripts/migrate.js`. Запускается **своим** `npm run migrate` в game-server.
- Никогда: игровые таблицы в основной БД, форумные — в игровой, мигратор одного сервиса
  на БД другого.
- `user_id` — логическая ссылка без FK (разные базы).
- Кастомные карты — `JSONB` (документ Tiled): валидация схемы до записи, лимит размера
  (рекомендуется ≤ 2 МБ), индекс `(owner_id, updated_at)`.
- «Горячее» состояние (позиции онлайн-игроков, содержимое комнат) — **только в памяти
  процесса**. В БД — персистентное: миры, карты, постройки, статистика, логи чата.
- Для ИИ: при генерации миграций помни — повторный запуск обязан быть безопасным.

## 7. Realtime-сервер: обязательные требования

1. **Авторитарность.** Сервер валидирует всё, что шлёт клиент: скорость, телепорт,
   границы карты, действия. Клиент — только контроллер и рендер. Клиент-авторитарная
   логика запрещена (читеры).
2. **State в памяти.** Онлайн-игроки и активные миры — объекты RAM. При старте —
   загрузка персистентного из БД; при изменениях — отложенный сброс (debounce);
   при остановке — финальный flush.
3. **Interest management (AOI) — требование №1 к коду синхронизации.** Игроку
   рассылаются только сущности в его окрестности. Без этого открытый мир не переживёт
   и десятка игроков по трафику и CPU.
4. **Частоты.** Клиент → сервер: 10–20 Гц. Сервер → клиент: снапшоты интересной зоны
   10–20 Гц. Чаще не нужно.
5. **Комнаты-«сервера».** Каждый игровой мир = отдельная комната со своим тик-циклом
   (`setInterval`) и списком подписчиков. Пустые комнаты выгружаются из памяти.
6. **Heartbeat.** ping/pong каждые ~30 с; мёртвые соединения закрываются.
7. **Rate-limit** на игровые действия и чат — in-memory, как на форуме (для одного
   процесса это нормально; Redis понадобится только при горизонтальном масштабировании).
8. **Graceful shutdown.** По SIGTERM: перестать принимать новых → разослать `closing` →
   сбросить персистентное в БД → закрыть WS и HTTP → `process.exit(0)`. Плюс
   `restart: unless-stopped` — контейнер поднимется сам.

Данные сессий переживают рестарт только если успели уйти в БД (см. п. 8). Потеря
in-memory-позиций при рестарте — допустимое и осознанное поведение.

## 8. Фронтенд: game.html — третье SPA

- Отдельная оболочка `public/game.html` (паттерн `chats.html`). Игру **не** встраивать
  в `index.html`/`chats.html` и не грузить Phaser на страницах, где он не нужен.
- Порядок `<script>`: `api.js` → `theme.js` → `ui.js` → `js/game/*.js` (config,
  ws-клиент, роутер, сцены). Всё глобальными неймспейсами, без модулей и сборки.
- Переиспользовать: `API.get/post/…` (токен подхватится из localStorage), `UI.esc()`
  для всего пользовательского контента (ники, названия миров, чат), тосты/модалки,
  `Theme` — смена темы на форуме меняет и игру.
- Стиль: `css/game.css` наследует токены `:root` из `style.css` (подключить style.css
  и переопределить нужное). Игра обязана выглядеть частью M-o-chi.
- Hash-роутинг свой: `#/game` (лобби/список серверов), `#/game/world/:id`,
  `#/game/editor`. Не пересекается с маршрутами форума и чатсов.
- **Dev-режим без nginx**: страница игры открыта с `:3000`, адрес игры задаётся в
  `js/game/config.js`: в проде `GAME_API_BASE='/game'`, `GAME_WS_URL='/game/ws'`;
  в dev — `http://localhost:3001` и `ws://localhost:3001/ws`.

## 9. docker-compose и запуск

Добавка к существующему `docker-compose.yml`:

```yaml
  game-db:
    image: postgres:16-alpine
    container_name: mochi-game-db
    restart: unless-stopped
    environment:
      POSTGRES_DB: mochi_game
      POSTGRES_USER: mochi_game
      POSTGRES_PASSWORD: game_secret
    ports:
      - "5434:5432"          # только для dev; в проде убрать
    volumes:
      - pgdata_game:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U mochi_game -d mochi_game"]
      interval: 5s
      timeout: 5s
      retries: 10

  game:
    build:
      context: .
      dockerfile: game-server/Dockerfile.game
    container_name: mochi-game
    restart: unless-stopped
    depends_on:
      game-db:
        condition: service_healthy
    environment:
      PORT: 3001
      DATABASE_URL: postgres://mochi_game:game_secret@game-db:5432/mochi_game
      JWT_SECRET: change-me-super-secret-in-production   # ТОТ ЖЕ, что у app!
      MAIN_API_URL: http://app:3000
    ports:
      - "3001:3001"
    mem_limit: 512m          # игра не должна задушить форум при утечке

volumes:
  pgdata_game:
```

- В production наружу публикуются только 80/443 (nginx). Порты БД (5433/5434) — dev-only.
- `Dockerfile.game` — по образцу основного: node:20-alpine, `CMD` = миграции игры + node.
- Проверка изоляции: `docker kill mochi-game` → форум продолжает отвечать;
  `docker restart mochi-game` → игра поднялась. И симметрично для `mochi-app`.

## 10. Порядок внедрения (этапы)

1. **Каркас `game-server/`**: package.json (express, pg, ws, dotenv; bcryptjs НЕ нужен —
   регистрации нет), `src/index.js` с `GET /api/health`, `config/db.js`.
   Проверка: `curl localhost:3001/api/health`.
2. **Инфраструктура**: `Dockerfile.game`, сервисы `game`/`game-db` в compose,
   nginx-локации из §3. Проверка: сайт и игра отвечают на одном домене;
   `https://домен/game/api/health` проксируется.
3. **Миграции игры** (001_init: миры, карты, участники, статистика, лог чата) +
   `npm run migrate` в game-server.
4. **Auth**: middleware проверки JWT тем же секретом; внутренний эндпоинт на основном
   сервере (`/api/internal/user/:id`) + кэш в game-server.
   Проверка: REST/WS игры пускает с токеном форума и не пускает без него.
5. **WS-каркас**: echo-сервер + auth-кадр + heartbeat + комнаты.
   Проверка: два браузера, сообщения ходят туда-обратно.
6. **REST игры** по конвенциям `PROJECT_CARD.md` §10: `v.*`-валидаторы, `ApiError`,
   `asyncH`, ошибки `{"error": "..."}` — утилиты копируются в `game-server/utils/`
   и адаптируются.
7. **Фронтенд**: `game.html` + `css/game.css` + `js/game/*`, интеграция `Theme`/`API`/`UI`.
8. **Проверка изоляции** (§9) и graceful shutdown (§7.8) — обязательные этапы, не опция.

Правило для ИИ на каждом этапе: проверяй, что не написал ни одного игрового файла
в `server/` и ни одной форумной сущности в игровой БД.

## 11. Безопасность (минимум)

- Параметризованный SQL (pg) — как на форуме. Никакой конкатенации SQL.
- Весь пользовательский контент на фронте — через `UI.esc()`. Если появится rich-HTML —
  только allowlist-санитайзер (порт `server/src/utils/post-utils.js`).
- Валидация входа `v.*`-хелперами + лимиты размеров (карты ≤ 2 МБ, чат-сообщения ≤ N символов).
- Rate-limit на REST-эндпоинты игры и игровой чат.
- `helmet` на игровом Express (CSP можно оставить отключённым, как на форуме).
- Проверять `Origin` при WS-upgrade (разрешён только свой домен).
- Tiled-JSON — только данные: никаких исполняемых полей, никакого eval.
- Не логировать токены; в access-логи токен не должен попадать (см. §5.2 про auth-кадр).

## 12. Грабли

1. nginx: WS без `proxy_http_version 1.1` + `Upgrade`/`Connection` не работает; без
   увеличенного `proxy_read_timeout` рвётся через ~60 с.
2. `JWT_SECRET` обязан быть одинаковым в env обоих сервисов; рассинхрон = 401 у всех
   игроков с непонятной ошибкой.
3. `depends_on: condition: service_healthy` для game-db — иначе игра стартует раньше БД.
4. Миграции игры — отдельный журнал в отдельной БД; мигратор основного сайта на неё
   не запускать.
5. Порты 5433/5434 наружу — только dev; в проде БД не публикуются.
6. Рестарт контейнера игры теряет in-memory-состояние — это ок при работающем
   graceful shutdown (§7.8).
7. `mem_limit` спасает форум от утечки в игре, но сам убивает процесс по OOM — поэтому
   `restart: unless-stopped` обязателен.
8. SPA-fallback основного сервера (`app.get('*')`) не должен перехватывать `/game/*`:
   в production их перехватывает nginx; в dev игра открыта как `game.html` со статикой
   основного сервера, а REST/WS идут напрямую на `:3001` (§8).

## 13. Анти-паттерны (что НЕ делать)

- ❌ Монтировать игровые роуты в `server/src/index.js`.
- ❌ Заводить игровые таблицы в основной БД «пока по-быстрому».
- ❌ Смешивать зависимости: ничего из игры в `server/package.json` и наоборот.
- ❌ Вводить TypeScript/сборку/фреймворки ради игры — стек проекта единый.
- ❌ Клиент-авторитарная логика (клиент решает, где игрок).
- ❌ Синхронизация позиций через БД или REST-поллинг.
- ❌ Микросервисная нарезка игры на много сервисов — изоляция нужна ровно одна:
  игра отдельно, сайт отдельно.

## 14. Отделять ли Mochi chats по этой же схеме? — НЕТ

Краткий ответ: **не стоит**, усилия не окупятся. Чатсы уже «сликом» интегрированы, и это
правильное состояние для их текущей нагрузки.

Почему чатсы не нуждаются в изоляции:

- Технически это **CRUD + HTTP-поллинг** (бейдж раз в 20 с, typing-флаги): без WebSocket,
  без долгоживущих соединений, без состояния в памяти, без тик-циклов. В отличие от игры,
  тут почти нет кода, способного уронить процесс.
- Изоляция уже существует на уровне кода: отдельный роутер `routes/gchats.js` и отдельное
  SPA `chats.html`. Сбой локализуется внутри одного файла и одной страницы.
- Одна БД и один JWT — фича, а не риск: чатсы активно ссылаются на общий аккаунт
  (упоминания @ник, бейджи, кастомные роли, ЛС). Разделение БД разорвёт FK `gchat_*` →
  `users` и породит синхронизацию данных между базами.
- Цена разделения высока: перенос 10+ таблиц (миграции 005–007), дублирование auth,
  резка самого большого файла проекта (`gchats.js`, ~72 КБ, ~45 эндпоинтов), новые
  nginx-локации, второй деплой-процесс — ради защиты от сбоя, вероятность которого мала,
  а последствия ограничены.

Когда пересмотреть решение (любой из триггеров):

1. Чатсы получат WebSocket/SSE — появятся долгоживущие соединения и состояние в памяти.
   Даже тогда первым шагом делается WS **внутри основного сервера** (паттерн из §7
   применим и там), и лишь при реальной нестабильности — вынос по схеме из этого файла.
2. Поллинг чатсов начал деградировать форум (тысячи RPS). Первое средство — кэш, индексы,
   SSE, Redis; разделение — последнее.
3. У чатсов появилась тяжёлая специфика (медиа-звонки, крупные файлы), требующая иных
   лимитов и зависимостей.

Вывод: игра выносится, потому что **создаёт новые классы рисков** (реалтайм-цикл, память,
CPU). Чатсы этих рисков не создают — им изоляция не нужна.

## 15. Финальный чеклист

- [ ] В `server/` нет ни одного игрового файла/зависимости (проверяется поиском `require`).
- [ ] В основной БД нет игровых таблиц, в игровой — форумных.
- [ ] `docker kill mochi-game` не роняет форум; `docker kill mochi-app` не роняет игру
      (активные сессии живут на кэше, новые отклоняются с понятной ошибкой).
- [ ] Единый `JWT_SECRET` у обоих сервисов; вход в игру — с токеном форума.
- [ ] nginx: `/`, `/game/`, `/game/ws` на одном домене; Upgrade-заголовки на месте.
- [ ] Токен в WS — первым кадром, не в URL.
- [ ] Interest management включён (рассылка ограничена окрестностью игрока).
- [ ] SIGTERM → flush в БД → закрытие отрабатывает; контейнер поднимается сам.
- [ ] Тема с форума применяется в игре (`Theme` общий).
- [ ] Миграции игры идемпотентны (повторный запуск без ошибок).
- [ ] В production наружу открыты только 80/443.
